# Database

The application's persistence layer, built with [Drift](https://drift.simonbinder.eu/).

This package contains the application's **V2 database** and its schema definitions. It exists to provide a stable, type-safe persistence boundary for new features while allowing the legacy database to be deprecated incrementally.

## Why AppDatabaseV2?

The original `AppDatabase` contains tables that were added alongside individual features over time. As the application evolved, this resulted in database definitions becoming tightly coupled to the old feature structure.

Moving the existing schema wholesale would require a large and potentially risky migration.

`AppDatabaseV2` provides a clean starting point instead:

* The existing `AppDatabase` remains available for legacy features.
* `AppDatabaseV2` is used for all new persistence.
* New features must not add tables to the legacy database.
* Existing features can migrate their data and persistence incrementally.
* Once the legacy database has no remaining consumers, it can be removed.

This allows the application architecture to evolve without requiring a single large database migration.

## Structure

```text
lib/
├── app_database_v2.dart
├── app_database_v2.g.dart
├── app_database_v2.steps.dart
├── database.dart
└── tables/
    ├── plans.dart
    └── tables.dart
```

### `app_database_v2.dart`

The main Drift database definition.

It is responsible for:

* Declaring the tables belonging to V2.
* Declaring DAOs when applicable.
* Defining the database schema version.
* Defining database migrations.

There must be **one `AppDatabaseV2` instance** for the application's V2 database.

### `tables/`

Contains the Drift table definitions used by `AppDatabaseV2`.

Tables should be organized according to the feature or domain they belong to.

For example:

```text
tables/
├── billing/
│   ├── plans.dart
│   ├── subscriptions.dart
│   └── entitlements.dart
│
└── timetable/
    └── timetables.dart
```

As the database grows, table definitions should remain separated into focused files rather than being placed directly inside `app_database_v2.dart`.

### Generated files

The following files are generated by Drift and **must not be edited manually**:

```text
app_database_v2.g.dart
app_database_v2.steps.dart
```

They should be regenerated whenever the database schema changes.

## Package Boundary

This package owns **persistence**, not business logic.

It is responsible for:

* Database connections.
* Drift table definitions.
* Database relationships and constraints.
* Queries and DAOs.
* Schema versions.
* Database migrations.
* Persistence-specific types.

It is **not** responsible for:

* Business rules.
* Feature use cases.
* BLoCs or other presentation logic.
* API clients.
* Authentication.
* Navigation.
* UI.

The dependency direction should remain:

```text
Feature
   │
   ▼
Repository / Data Source
   │
   ▼
Database package
   │
   ▼
Drift / SQLite
```

The database package should never depend on feature packages.

## Public API

`database.dart` is the package's public entry point.

Consumers should import:

```dart
import 'package:database/database.dart';
```

rather than importing files from `src` or relying on internal implementation paths.

Only APIs intended for consumption outside the package should be exported from `database.dart`.

For example:

```dart
export 'app_database_v2.dart';
export 'tables/tables.dart';
```

Generated implementation details should generally **not** be exported unless consumers genuinely need them.

## Database Ownership

There is one physical V2 database and one Drift database instance:

```text
                 Application
                      │
                      ▼
              AppDatabaseV2
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
        Plans     Timetable   Assignments
          │           │           │
          └───────────┴───────────┘
                      │
                    SQLite
```

Individual features must not create their own independent `AppDatabaseV2` instances.

The application/composition root is responsible for creating and providing the database instance.

## Legacy Database

The legacy `AppDatabase` and `AppDatabaseV2` are intentionally separate during the migration period.

```text
Legacy features ──────► AppDatabase

New / migrated
features ─────────────► AppDatabaseV2
```

The legacy database is considered **frozen**.

New tables should not be added to it unless required to support an existing legacy feature during the migration period.

When an existing feature is migrated:

1. Its V2 schema is introduced.
2. Existing data is migrated or transformed as necessary.
3. The feature is switched to `AppDatabaseV2`.
4. Its legacy database usage is removed.
5. Its old tables can eventually be removed from the legacy database.

## Schema and Migrations

`AppDatabaseV2` has its own schema version and migration history.

Schema changes must use Drift migrations rather than destructive database recreation.

For example:

```dart
@override
int get schemaVersion => 2;

@override
MigrationStrategy get migration => MigrationStrategy(
  onCreate: (Migrator m) async {
    await m.createAll();
  },
  onUpgrade: (Migrator m, int from, int to) async {
    // migrations
  },
);
```

The V2 schema should remain internally consistent and fully type-safe through Drift's generated APIs.

## Adding a New Table

When introducing persistence for a new feature:

1. Define the table under `tables/`.
2. Add the table to `AppDatabaseV2`.
3. Add any required DAO/query definitions.
4. Update the migration/schema version when required.
5. Regenerate Drift code.
6. Expose only the necessary database API through the package's public exports.

**Do not add the table to the legacy `AppDatabase`.**

## Design Principle

> **`AppDatabase` is legacy infrastructure. `AppDatabaseV2` is the database for all new and migrated persistence.**

The goal is not to maintain two databases permanently. The goal is to provide a safe migration path from the existing schema to a cleaner, maintainable persistence architecture without requiring a disruptive rewrite.
